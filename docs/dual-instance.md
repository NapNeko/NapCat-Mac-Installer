# Running NapCat and the native QQ client side by side

NapCat-Mac-Installer patches `/Applications/QQ.app` so that QQ started with
`--no-sandbox` loads NapCat, while QQ started without that flag is meant to
behave like the normal QQ client. This document describes the fix that makes
the second half work on QQ builds that have received a hot update, and the
launch panel that lets both run at the same time.

Typical use: a bot account runs headless through NapCat, and a different
account is used in the regular QQ window on the same Mac.

## Symptom

With NapCat running, starting the native client (`open -n -a /Applications/QQ.app`)
created a second `QQ` process that never showed a window. It stayed idle with
only menu-bar-sized windows, no renderer processes, no crash report and no
JavaScript error dialog.

## Root cause

QQ for macOS ships a small native stub (`QQ.app/Contents/MacOS/QQ`). When a hot
update is installed it loads the Electron runtime from
`~/Library/Containers/com.tencent.qq/Data/Library/Application Support/QQ/versions/<curVersion>/QQUpdate.app`
instead of the one inside `QQ.app`. The two runtimes can be different Electron
major versions. On the machine where this was investigated:

| Bundle | QQ version | `QQNT.framework` CFBundleVersion (Electron) |
| --- | --- | --- |
| `/Applications/QQ.app` | 6.9.96-49738 | 37.1.0 |
| `versions/7.0.2-53644/QQUpdate.app` | 7.0.2-53644 | 40.0.0 |

Both bundles' `package.json` point `main` at `loadNapCat.js`. The previous
loader's non-NapCat branch always did:

```js
require('/Applications/QQ.app/Contents/Resources/app/app_launcher/index.js');
```

`app_launcher/index.js` is a stub that loads compiled code from the
neighbouring `major.node`. The process was therefore running Electron 40 while
executing the launcher built for the base bundle. Evidence collected from the
stuck process:

- `lsof` showed the base bundle's `major.node` mapped next to the hot-update
  `QQNT.framework`.
- The launcher log (`log/app_launcher-*.log`) and `updater.log` received no
  entry at all for that start. Every successful start writes several lines
  there before creating a window.
- No `BrowserWindow` and no renderer process was ever created.

Why the base launcher fails silently on the newer runtime was not determined
(its code is loaded from the native `major.node` addon and no source is
available). The fix does not depend on it.

Running the hot-update bundle's own launcher, which is what QQ does without the
loader, made the window appear immediately.

## Fix

### Loader (`loadNapCat.js`, generated by `Utils.swift`)

The `--no-sandbox` branch is unchanged. In the other branch the loader:

1. Builds the candidate list: the bundle named by `curVersion` in
   `versions/config.json` (if present), then the base `QQ.app`.
2. Reads `CFBundleVersion` from each candidate's
   `Contents/Frameworks/QQNT.framework/Resources/Info.plist`.
3. Picks the candidate whose version equals `process.versions.electron`,
   i.e. the runtime that is actually executing.
4. Checks that `app_launcher/index.js` and `major.node` exist there, then
   requires it.
5. If nothing matches, or the files are missing, it throws an error naming
   every candidate and its Electron version. It never falls back to a launcher
   built for a different runtime.

The existing `global.launcher.installPathPkgJson.main` adjustment is kept as is.

The installer no longer rewrites the loader on every "switch to NapCat":

| Existing `loadNapCat.js` | Action |
| --- | --- |
| missing or the previous generated version | write the new loader |
| identical to the new loader | leave untouched |
| anything else (user-modified) | keep it; it can be replaced from the launch panel, which backs it up to `loadNapCat.js.bak-<timestamp>` first |

### Launch panel (`ContentView.swift`, `DualOpen.swift`)

The panel shows live status, re-read from the process table every 2 seconds:

- NapCat: running / not running, with PID.
- Native QQ: running / not running, with PID and window state (visible, not on
  the current desktop, or no window).
- Loader state, the launcher that will be used (hot-update version and Electron
  version), and hot-update bundles whose entry point still has to be redirected.

Instances are identified by the main executable path
(`/Applications/QQ.app/Contents/MacOS/QQ`, compared exactly via `proc_pidpath`)
and by whether `--no-sandbox` is in the process arguments (`KERN_PROCARGS2`),
which is the same rule the loader uses. Helper processes, TIM and any other
application never match.

| Action | Before | After |
| --- | --- | --- |
| Start NapCat | `killall -9 QQ QQEXDOC`, then run in the selected Terminal tab | No-op if NapCat already runs. Syncs hot-update entry points, then opens a **new** Terminal window. Never stops other QQ processes. |
| Start native QQ | `killall -9 QQ QQEXDOC`, restore the original `package.json` with sudo, `open` QQ | Activates an existing native instance if there is one. Otherwise `open -n /Applications/QQ.app` without `--no-sandbox`, while NapCat keeps running. Refuses to start with an outdated or missing loader or an incomplete launcher. |
| Stop | not available (only `killall -9` as a side effect) | Per instance, after confirmation. Re-verifies PID, start time and mode, requests a normal quit, falls back to SIGTERM after 10 s. SIGKILL is never sent. |

`com.apple.security.automation.apple-events` was added to the entitlements so
that activating an instance and requesting a normal quit also work in builds
signed with the hardened runtime (the project enables it, CI release builds
are re-signed without it).

## Hot updates and full QQ updates

| Situation | Behaviour |
| --- | --- |
| No hot update | Base `QQ.app` launcher is used. |
| Hot update active | `versions/<curVersion>/QQUpdate.app` launcher is used. |
| Another hot update arrives | `curVersion` changes and the loader follows it. Its new `package.json` still points to QQ's own entry, so NapCat would not load; the panel reports this and "Start NapCat" redirects it before launching. |
| Hot-update bundle incomplete or runtime mismatch | The loader throws with the details. The panel shows the problem and blocks "Start native QQ". |
| Full QQ update (new `QQ.app`) | `package.json` is replaced, so the entry status shows "original QQ" again. Switching to NapCat re-patches it and refreshes the `.bak`. The loader is kept. |

QQ's own update mechanism is not disabled.

The UI checks found and fixed two issues before submission: PIDs were shown
with digit grouping (`58,901`) in labels created from string literals, and long
error messages were truncated to one line.

The new launch panel's start and stop buttons have only been exercised against
the mock controller, not against real QQ processes.

## Known limitations

- Both instances share `~/Library/Containers/com.tencent.qq/Data`, including
  `global/nt_db/login.db` and `global/nt_data/mmkv`. Each account keeps its own
  `nt_qq_*` directory and no conflict was seen during testing, but long-running
  concurrent use is not proven. Logging into the same account in both
  instances is not supported.
- The panel's launcher check mirrors the native stub's choice of runtime
  (hot-update bundle if its framework exists). That rule was inferred from
  logs, so the check is advisory; the loader's runtime check is authoritative.
- Activating a native instance that has no window sends a "reopen" Apple Event
  to that PID. Whether macOS asks for automation consent for this event was not
  verified.
- Stopping a NapCat instance that was started from Terminal has not been
  exercised against a real process.
